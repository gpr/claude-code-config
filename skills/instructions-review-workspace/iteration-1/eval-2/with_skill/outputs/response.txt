# incident.io

All tools below are on the `incident_io` MCP server (runtime prefix
`mcp__incident_io__`); they are referred to by bare name from here on.

Auth lives in the macOS Keychain. On 401/403, tell the user to reauthenticate
in the incident.io macOS app. On 404, verify the incident ID. Local tools keep
working when the backend is unreachable; `ask` and `ask_incident` do not.

## Workflow

1. **Find the incident.**
   - ID given, or "my incident" / "the incident" → `incident_pin(incident_id=…)`
     to set it, or `incident_pin()` with no args to read the current pin.
   - Nothing given ("I got paged") → `escalations_list`, look for the user's
     email and `← YOU` markers, then offer the top 3–5 as one-line summaries
     via `AskUserQuestion`. Recommend one if it's clearly most relevant. Never
     dump full escalation details.
2. **Pin it** before doing any other work — the pin drives the macOS app and
   the PR footer below. `incident_pin(unset=true)` clears it.
3. **Get context.** `ask_incident` for a narrative summary, or
   `incident_show(include: ["investigation", "postmortem"])` for structured
   data — the default response is metadata only and omits the AI investigation
   findings and post-mortem.
4. **Help the user** — read code, analyse data, debug.
5. **Share findings** with `incident_message` (see Posting to a channel).

## Choosing a tool

Prefer the data tools (`incident_*`, `alert_*`, `escalation_*`, `follow_up_*`,
`schedule_*`, `catalog_*`) for counts, filtering, and specific fields — they
are faster and cheaper than the agent tools. Reach for `ask` / `ask_incident`
only when you need AI reasoning, entity resolution, or a multi-step action.

- `incident_stats`, `alert_stats`, `escalation_stats` — start here for any
  analytical question. `alert_stats` includes workload from linked incidents.
- `incident_list` — pass `include: ["roles"]` or `include: ["custom_fields"]`
  for analytical queries.
- `identity_get` — the user's name/email/ID, needed for attribution.
- Read the `config://organisation` MCP resource for severity, custom field,
  and role IDs before filtering on them.
- Read the `playbook://analysis` MCP resource before multi-step analytical
  work — it covers incident, alert, and escalation analysis strategies.

**Division of labour.** You analyse data, read code, and draft. `ask_incident`
performs incident actions (official updates, status/severity changes,
actions, follow-ups, role assignment). `ask` answers org-level questions
(on-call, catalog, schedules, schedule overrides). `incident_message` posts
analysis you did yourself.

## Agent tool sessions

`ask` and `ask_incident` return JSON with `session_id`, `response`, `outcome`,
and optionally `image_urls` and `suggestion`. Omit `session_id` on the first
call and on a new topic; pass the previous one to continue a thread (e.g.
asking a question, then accepting the resulting suggestion).

## @incident requests

Route by question type: incident actions → `ask_incident`; org queries →
`ask`. Verify destructive-sounding requests ("change status to resolved") make
sense before dispatching.

The backend agent cannot see your session — not the code you read, the fix you
pushed, or the PR you opened. Before dispatching, decide whether it needs that
context. "Change status to resolved" is self-contained. "Send an update" after
20 minutes of debugging is not: rewrite it as a self-contained question.

**Bad** — `question: "send an update"`. The agent has nothing to say.

**Good:**

```
question: "Send an update to say we found the trace image renderer was
spending ~2 minutes in a tight font glyph-loading loop, causing excessive
memory pressure on the worker-ai pod. We've pushed a fix in commit ff35f9c
that replaces the O(n^2) truncation loop with a single-pass truncateToWidth
approach."
```

## Suggestions

Ask `ask_incident` to generate suggestions ("suggest an incident update") —
don't draft them locally; the backend has the context and tools.

When a response carries a `suggestion` (`id`, `suggestion_type`, `content`),
always get the user's approval before actioning it. Present the parsed content
and offer accept / decline / update through `AskUserQuestion`. Field mappings
for `suggestion_type: update`:

- `incident_status_name` → "Status → {value}"
- `severity_id` → "Severity → {value}"
- `name` → "Name → {value}"
- `message` → show the message text

Describe `role`, `follow_up`, and `escalation` types from whichever content
fields are present. Then send a follow-up `ask_incident` on the same
`session_id`: `"accept suggestion <id>"`, `"decline suggestion <id>"`, or
`"update suggestion <id>, change severity to SEV-3"`. If the user moves on
without answering, don't action it.

## Represent the user faithfully

You are writing on behalf of a human — both in channel messages and when
presenting findings back to the user.

- **Match their certainty.** If they said "I believe X might be causing this",
  write "likely" / "appears to be" / "looks like". State something flatly only
  when they did. Prefer "the cause" over "root cause".
- **Match their framing.** They pushed a fix → they pushed a fix. Still
  investigating → say so. Describe what was done; don't reinterpret it.
- **Post only what they asked you to post.** If you've read investigation data
  but they haven't stated a finding, wait. Their conclusions, not yours.
- **Keep hedging in AI investigation findings** when relaying
  `incident_show(include: ["investigation"])` output.

## Posting to a channel

`incident_message` takes `message`, optional `thread_message`, and `user` (the
full name from `identity_get`, else "incident.io").

`message` — 1–2 sentences, first person, conversational. `inline code` for
paths, functions, and values; **bold** sparingly for outcomes; hyperlinks as
`[text](url)`. No emojis, headers, or bullets. If there are details, put them
in the thread and say "see thread".

`thread_message` — full technical detail: code blocks, logs, bullet lists.
**Bold** for section titles, not markdown headers. Sentence case throughout.
Skip the thread entirely for simple status updates and confirmations.

**Confirmed fix:**

```
message: "Pushed a fix for the connection pool exhaustion — there was a
missing index on `users.email`. Query time `5s → 50ms` (PR#5678). See
thread for details."

thread_message: "**What happened**\n\nThe `users` table was doing full
table scans on every login..."
```

**Still investigating:**

```
message: "Looked into the connection pool exhaustion — it looks like a
missing index on `users.email` might be the cause. Still confirming.
See thread for what I've found so far."
```

## Presenting data to the user

- Lead with the reference: INC-123, severity, status.
- Workload from the stats tools is in **minutes** — present hours: "42 hours
  of responder time (8 hours overnight)".
- For stats results, lead with the most impactful groups (highest count, most
  workload, biggest change over time) rather than listing everything.
- Connect alerts to incidents explicitly: "Alert X from Datadog triggered
  INC-123, which consumed 12 hours of responder time."
